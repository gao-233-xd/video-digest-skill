# 转写流程详解

本文档按 bbdigest.py 的实际执行顺序，逐阶段说明每一步做了什么、为什么这么做。
对应源码均为 `bbdigest.py`，可对照阅读。

## 0. 环境准备

- **HuggingFace 镜像**：`HF_ENDPOINT=hf-mirror.com`、`HF_HUB_DISABLE_XET=1`。
  镜像站不支持 Xet 下载协议，不禁用新版 huggingface_hub 会在解压 Brotli 时崩溃。
  另外依赖里钉死了 `huggingface_hub<1.0` 和 `av<19`（av 19 移除了 faster-whisper 依赖的
  `av.open(metadata_errors=...)` 参数）——版本钉子的原因都写在 requirements.txt 注释里。
- **GPU 动态库**：Windows 上通过 pip 装 `nvidia-cublas-cu12` / `nvidia-cudnn-cu12` 提供算力库，
  运行时用 `os.add_dll_directory()` 注册（幂等——批量任务反复调用时若重复追加 PATH
  会撑爆 Windows 的 32KB 环境变量上限）。
- **模型进程内缓存**：`_MODEL_CACHE` 按 (模型名, 设备, 精度) 缓存 WhisperModel 实例，
  批量处理多个分P时避免反复加载。

## 1. 链接解析（`parse_input`）

| 输入 | 处理 |
|---|---|
| b23.tv 短链 | requests 跟随 302 跳转，取最终 URL |
| 完整URL | 正则 `[Bb][Vv][0-9A-Za-z]{10}` 提取 BV 号 |
| av号 | 提取数字，走 `aid` 参数的 API |
| URL 带 `?p=N` | 解析出分P提示，run 时只处理该P |

## 2. 视频信息（`fetch_view`）

- API：`api.bilibili.com/x/web-interface/view`，带 `SESSDATA`/`buvid3` Cookie 和 Referer。
- `rights.is_upower_exclusive` 为真 = 充电专属视频，直接报错终止（下载不了）。
- 分P清单来自返回的 `pages` 数组（每P有 page/part/duration/cid）。
- **合集识别**（`notice_season`）：B站"合集"是多个独立视频的集合，不是分P。
  通过 `seasons_archives_list` API 查合集元信息，只在日志里提示"合集≠分P"，
  避免用户以为 `--pages all` 能跑完整个合集。

## 3. 字幕获取：三重防线防"换源残留字幕"

UP主换过视频源后，B站后台可能残留**旧视频的AI字幕**——时长可能恰好和现视频接近，
单纯看时长发现不了，一旦混入，转写内容就全错了。所以有三道防线：

### 防线一：只对 >10 分钟的视频启用官方字幕

短视频（≤600s）本地转写本来就只要几十秒，不值得为省这点时间冒字幕残留的风险，
直接跳过字幕抓取。

### 防线二：时长覆盖校验（`fetch_subtitle`）

拿到字幕段落后检查最后一条的结束时间 `last_end`：

- `last_end > duration × 1.15 + 5s` → 字幕比视频还长，是换源残留 → 弃用
- `last_end < duration × 0.4` → 只覆盖前半段，疑似残缺 → 弃用

### 防线三：内容抽检（`_spot_check_subtitle`）

时长校验拦不住"换源后时长恰好相近"的情况，只能**内容比对**：

1. 在视频 20% / 50% / 80% 处各取一个 30 秒的音频窗口（ffmpeg 切片）；
2. 用 Whisper 快速转写这三个窗口（复用正式转写的模型，缓存共享）；
3. 把转写文本与官方字幕同一时间段的文本做 `SequenceMatcher` 相似度比对；
4. **最大相似度 ≥ 0.15** 才放行（阈值很低——只要求"说的确实是同一件事"，
   因为官方字幕和Whisper转写的断句、标点、语气词差异本来就大）；
5. 有效采样不足 2 个窗口时保守放行（可能是无人声/音乐段落）。

抽检通过 → 直接使用官方字幕，**秒级完成，跳过整个本地转写**；
抽检不符 → 打日志说明原因，弃用字幕，回落本地转写。

字幕选择上还有个小细节：UP主上传的CC字幕和B站生成的AI字幕可能同时存在，
按 `lan` 字段排序，`ai` 开头的（AI字幕）优先。

## 4. 本地转写（`transcribe_audio`，faster-whisper）

### 降档链

```
medium / cuda / int8_float16   ← 默认，画质精度最优
  ↓ 显存不足等异常
small  / cuda / int8_float16   ← 更小的模型，仍在GPU
  ↓ 再失败
small  / cpu  / int8           ← CPU兜底，慢但总能跑完
```

每一档失败都打日志说明异常类型，保证"总能出结果，只是慢"。

### VAD 人声过滤

```python
vad_filter=True,
vad_parameters=dict(threshold=0.35, min_silence_duration_ms=700, speech_pad_ms=400)
```

- 过滤背景音乐、静音段，显著提升纯talk类视频的转写质量、降低幻觉；
- 副作用：对纯音乐/歌声类视频可能过度过滤（一段语音都检不出来）——
  此时自动**关闭 VAD 重试一次**，两版结果取非空者。

### 转写参数

- `language=auto`（config.ini 可固定 zh）；
- whisper 的 transcribe 返回生成器，逐段消费（这是"转写全程无进度输出"的原因），
  全部段落在内存里聚合后再一次性写文件。

## 5. 关键帧截取（`extract_frames`）

四步流水线：

### ① ffmpeg 场景检测

```
-vf "select='gt(scene,0.3)',showinfo,scale=1280:-2"
```

- `scene` 滤镜给每帧打 0~1 的场景切换分数，超过阈值(默认0.3)的帧被选出；
- 从 showinfo 的 stderr 里解析 `pts_time` 拿到精确时间点；
- 统一缩放到 1280 宽，控制文件体积。

### ② 双重去重

- **时间去重**：相邻选中帧间隔 < 2 秒的丢弃；
- **感知去重**：对每张帧算 pHash（感知哈希），与最近 3 张保留帧的
  汉明距离 ≤ 8 视为重复丢弃——专治"字幕轻微变化但画面没动"的假场景切换。

### ③ 静止画面兜底

教程类视频（PPT录屏、人肉口播）可能全程没有一次场景切换。兜底策略：

- 有选中帧：开头(>5s时)补一张 t=0.5s，相邻帧间隔超过 `fallback_interval`(默认240s) 时中间补帧；
- 完全无选中帧：从 0.5s 开始每 240s 固定截一张，结尾再补一张。

### ④ 归位命名

帧文件按时间点命名（`00-05-32.jpg`），**文件名即时间戳**，重名加 `-1` 后缀。
原始帧在 `_raw` 临时目录处理完即删。

## 6. 产物写入

- **transcript.md**：把零散的 whisper 段落聚合成可读段落——
  距上一段开始超过 30s 或间隙 > 2s 就另起一段，段首标 `[mm:ss]` 时间戳；
  中英混排时前尾均为拉丁字符才补空格（中文不加空格）。
  无语音（可能是纯音乐）时写明"未检测到语音内容"。
- **transcript.srt**：同内容的标准字幕，段末最短 0.2s，导入播放器可对照回看。
- **info.json / cover.jpg**：元数据与封面，供 Agent 和人工归档用。
- 目录名 = `标题-UP主-发布日期`（各部分做文件名非法字符清洗和长度截断）。

## 7. 增量与断点

`page_done_marks` 检查某P是否已有 transcript.md / frames 产物（兼容单P扁平布局
和多P子目录布局两种），已处理的P在 run 时自动跳过——
挂掉重跑、追加处理分P都不做重复劳动。`--force` 才全部重新生成。

## 8. 实战经验（写给 Agent 和重度用户）

这些是文档写不出来、只能踩坑换来的经验，已写入 SKILL.md：

1. **转写静默是正常的**：faster-whisper 全程无进度输出，判断是否在工作看进程 CPU 时间
   是否增长、日志是否推进到下一阶段（下载视频→场景检测）。
2. **严禁同一台机器并行跑两个转写**：小显存（≤4GB）显卡跑两个 Whisper 进程会触发
   WDDM 把显存溢出到系统内存（可用性能计数器 `GPU Process Memory\Shared Usage` 观测，
   每进程溢出100MB+即为颠簸），两个任务互相拖慢数倍。串行处理；若已在并行且卡死，
   杀掉一个让另一个独占 GPU 通常比继续等更快。
3. **多P视频先 info 再跑**：让用户确认范围，避免误跑几十个P。
4. **`--no-frames` 的适用场景**：播客、纯口播类视频画面无信息量，跳过截帧能省一半时间
   （不用下载几百MB的视频文件）。
5. **产物阅读顺序**：先 transcript.md 通读，再用 2-3 张关键帧校正专有名词
   （转写是语音识别，"姬叉"可能被写成"季叉/集叉"），最后写总结。
